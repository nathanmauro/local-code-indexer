# Pre-commit audit — 2026-06-10

Adversarial multi-agent review of the full codebase before its initial commit.

**Method:** 4 dimension-specific reviewers (correctness, security, data-integrity, API/packaging) each read the entire package and reported up to 6 falsifiable findings. Every finding was then independently judged by a 3-agent refuter panel (exploit-reproduction, code-reading, and design-intent lenses), each instructed to refute by default; a finding survives only with 2 of 3 non-refuted votes. 76 agents total. Several findings were confirmed by live reproduction against the project venv.

**Result: 19 confirmed, 5 rejected.** Findings the panel rejected are listed at the bottom and were NOT fixed.

## Confirmed findings

### 1. [HIGH] sqlite-vec KNN query is missing the required k constraint, so vector search via sqlite-vec always fails and silently falls back to a full-table JSON cosine scan

`src/local_code_indexer/service.py:549` — api-packaging — panel 3/3 upheld

**Claim:** The vec0 KNN query in _add_vector_candidates ('WHERE v.embedding MATCH ? ... ORDER BY v.distance LIMIT 100' with three JOINs) always raises sqlite3.OperationalError on sqlite-vec 0.1.9 because the outer LIMIT is not pushed into the virtual table and no 'k = ?' constraint is given. The except branch swallows the error, so the sqlite-vec index that index_repo dutifully populates is never used for any query; every vector/hybrid search runs the O(n) embedding_json cosine fallback instead. The README claim that the project 'uses sqlite-vec when available for vector search' is therefore false at query time.

**Evidence:** Reproduced against the venv's sqlite-vec 0.1.9 with the exact table shapes and SQL from service.py: the query fails with "A LIMIT or 'k = ?' constraint is required on vec0 knn queries."; changing the WHERE clause to 'WHERE v.embedding MATCH ? AND k = 100' returns correct rows. In service.py the failure is caught by 'except sqlite3.OperationalError: used_sqlite_vec = False' (line 561-562), after which the JSON fallback runs unconditionally — there is no log, no status signal, and the tests never exercise the loaded-extension query path.

**Suggested fix:** Add the k constraint: select KNN rowids in a subquery ('SELECT rowid, distance FROM chunk_vectors WHERE embedding MATCH ? AND k = ?') and join chunks/repos around it (the repo filter must apply after KNN, or over-fetch and filter in Python). Also stop swallowing the OperationalError silently — at minimum record it so code_index_status can report 'sqlite_vec: loaded' vs 'query fallback', and add a test that runs a vector search with the real extension loaded.

### 2. [HIGH] All MCP tools are sync functions executed directly on the asyncio event loop; code_index_search makes a blocking 10s-timeout HTTP call to Ollama, starving the stdio server

`src/local_code_indexer/tools.py:29` — api-packaging — panel 2/3 upheld

**Claim:** FastMCP (mcp 1.27.2, the installed SDK) calls non-async tool functions directly on the event loop thread — func_metadata.py line 96 is 'return fn(**arguments_parsed_dict)' with no to_thread offload. Every tool here is a sync def, and code_index_search in hybrid/vector mode calls LocalEmbedder.embed(), a blocking urllib.request.urlopen with timeout=10.0 (embeddings.py line 38). While Ollama computes (or while a cold model loads, easily multiple seconds), the entire stdio server is frozen: no concurrent tool calls, no ping responses, no cancellation handling. The fallback cosine scan over every chunk's embedding_json and the per-call _service() (which re-runs the full CREATE TABLE executescript and constructs a new connection on every single tool invocation) block the loop too.

**Evidence:** tools.py lines 28-36: '@mcp.tool()\ndef code_index_search(...) -> str: return _json(_service().search(...))' — sync def, _service() at line 17-21 builds a fresh IndexService + LocalEmbedder and calls service.init() per call. service.search() -> _embed_query() -> LocalEmbedder.embed() -> 'with urllib.request.urlopen(request, timeout=self.timeout)' (embeddings.py:38). Installed SDK confirmed: .venv/.../mcp/server/fastmcp/utilities/func_metadata.py lines 93-96 await async fns but call sync fns inline in the running coroutine.

**Suggested fix:** Declare the tools 'async def' and run the service work off-loop, e.g. 'return await anyio.to_thread.run_sync(lambda: _json(_service().search(...)))' (anyio ships with mcp). While there, hoist a single module-level IndexService so init()/DDL and embedder construction happen once at server start instead of per tool call.

### 3. [HIGH] Valid UTF-8 files silently excluded from index when a multibyte character straddles the 4096-byte sniff boundary

`src/local_code_indexer/ignore.py:96` — correctness — panel 3/3 upheld

**Claim:** _looks_binary decodes only the first 4096 bytes (sample = path.read_bytes()[:4096]; sample.decode('utf-8')). If a multibyte UTF-8 sequence is split exactly at byte 4096, the truncated sample raises UnicodeDecodeError and the file is classified as binary, so is_indexable returns False and the file is silently dropped from the index (and deleted from the index on reindex via _delete_missing_files if it was previously indexed). Any text file over 4KB containing non-ASCII characters is at risk; for CJK- or accented-comment-heavy files the probability of the boundary landing mid-character is high.

**Evidence:** Constructed a file of 4095 ASCII bytes followed by 'é' (0xC3 0xA9) plus normal Python code. The whole file decodes as UTF-8 ('whole file decodes as UTF-8: True', bytes 4094..4097 = ['0xa','0xc3','0xa9','0x20']), yet IgnoreMatcher reports _looks_binary: True, is_indexable: False, and iter_indexable_files yields nothing for the repo.

**Suggested fix:** Treat a decode error at the tail of the sample as truncation, not binary: catch UnicodeDecodeError and return True only when e.start < len(sample) - 3 (UTF-8 sequences are at most 4 bytes); alternatively use codecs.getincrementaldecoder('utf-8') with final=False. Also slice before reading the whole file (read only 4096 bytes) since read_bytes() currently loads the entire file just to sniff.

### 4. [HIGH] Embedder death mid-index commits a silently embedding-less index with no failure signal

`src/local_code_indexer/service.py:359` — integrity — panel 2/3 upheld

**Claim:** If the Ollama service dies (or hangs) partway through index_repo, every subsequent chunk is committed with embedding_json='' and no chunk_vectors row, the run reports success, and no surface (return dict, status(), logs) reveals the gap. Worse, if Ollama hangs rather than refusing connections, each remaining chunk blocks up to the 10s timeout inside the open write transaction.

**Evidence:** service.py:354-360: `def _embed_chunk(self, content): if self.embedder is None: return None; try: return [...]; except Exception: return None`. _insert_chunk (line 303-304) then stores `embedding_json = json.dumps(embedding) if embedding else ""` and skips _upsert_vector. index_repo's return dict (lines 217-224) has only indexed_files/indexed_chunks/deleted_files; status() (line 771) reports embeddings 'enabled' purely from `self.embedder is not None`, never from actual coverage. The final conn.commit() at line 215 persists the half-embedded state.

**Suggested fix:** Count embedding failures during index_repo and surface them in the result dict (e.g. chunks_embedded / chunks_embedding_failed) and in status() (SELECT COUNT(*) FROM chunks WHERE embedding_json = ''). Add a circuit breaker: after N consecutive embed failures, stop calling the embedder for the rest of the run (avoids per-chunk 10s timeouts) and flag the run as degraded so the next reindex can heal it deliberately.

### 5. [HIGH] One transient filesystem error aborts the whole index transaction and kills the watch loop

`src/local_code_indexer/service.py:191` — integrity — panel 3/3 upheld

**Claim:** A file deleted, truncated, or made unreadable between the is_indexable() check and read_bytes()/stat() (common in a live repo: git checkout, editor atomic saves, temp files) raises an uncaught OSError that rolls back the entire repo index and, under `local-code-indexer watch`, terminates the watcher process. Additionally stat() is taken after read_bytes(), so a file modified between the two calls records mtime/size from a different version than the bytes that were hashed and stored.

**Evidence:** service.py:191-194: `data = file_path.read_bytes()` then `stat = file_path.stat()` with no try/except anywhere in the per-file loop (lines 188-212); the exception escapes `with self._connect() as conn:` which rolls back all work. scanner.py:14 `sorted(root.rglob("*"))` materializes the full listing up front, widening the check-to-read window. cli.py:73-75: `while True: _print_json(service.index_repo(...)); time.sleep(...)` — no exception handling, so the poll loop dies on the first transient error.

**Suggested fix:** Wrap per-file processing in try/except OSError: skip the file, increment a skipped_files counter returned in the result dict, and continue. Stat once before reading (or use len(data) for size) so hash/size/mtime describe the same snapshot. In the CLI watch loop, catch exceptions per cycle, log, and continue polling.

### 6. [HIGH] Symlink escape: scanner indexes files outside the repo and bypasses SECRET_NAMES

`src/local_code_indexer/scanner.py:14` — security — panel 3/3 upheld

**Claim:** A file symlink inside the repo that points outside the repo is indexed: its target content is read and stored, the repo-root containment is defeated, and the SECRET_NAMES/SECRET_SUFFIXES checks are dodged because they inspect the link name, not the target. A malicious or cloned repo can exfiltrate ~/.aws/credentials, ~/.ssh/id_rsa, etc. into the searchable index, which is then retrievable via the code_index_search / code_index_read_file MCP tools.

**Evidence:** scanner.iter_indexable_files iterates `root.rglob("*")`, which yields symlink entries; `Path.is_file()` (ignore.py:103) follows the link and returns True. ignore._relative (ignore.py:72-77) does `path.resolve().relative_to(self.root)`; for an out-of-repo target this raises ValueError and falls back to `rel = path` (the link's absolute path), so `_hard_skip` parts never match HARD_SKIP_DIRS and `_spec.match_file(rel)` is given an absolute path that gitignore patterns won't match. service.index_repo (service.py:191) then does `file_path.read_bytes()` on the link, reading the off-repo target. Reproduced on Python 3.9/3.11/3.12/3.13: `repo/benign.txt -> ../outside/creds.txt` yields is_file=True, target=/private/tmp/symtest/outside/creds.txt, read content b'SECRET=topsecret\n', and _relative returns the absolute path. Because the secret check is `path.name in SECRET_NAMES`, a link named `benign.txt -> ~/.ssh/id_rsa` is also indexed despite id_rsa being on the blocklist.

**Suggested fix:** Reject symlinks before indexing: in IgnoreMatcher.is_indexable, return False when `path.is_symlink()` (or when `path.resolve()` is not within `self.root`). Anchor containment on the resolved real path: treat a file as indexable only if `path.resolve()` is relative_to(self.root). Apply secret/hard-skip checks against the resolved target name, not the link name. Also pass followlinks=False semantics by enumerating with os.walk(followlinks=False) or filtering symlinked dirs.

### 7. [HIGH] SECRET_NAMES is an exact-match allowlist that misses common secret files (.env.production, .env.*, certs)

`src/local_code_indexer/ignore.py:34` — security — panel 3/3 upheld

**Claim:** The hard-skip secret list only matches the exact names {.env, .env.local, .envrc, id_*} and suffixes {.pem,.key,.p12,.pfx}. Extremely common secret-bearing files are NOT skipped: .env.production, .env.staging, .env.development, .env.prod, .env.* in general, plus .crt, .cer, .pkcs8, .jks, credentials, .npmrc, .pgpass, .htpasswd, service-account JSON. These get fully indexed (content stored in SQLite and returned by search) unless a top-level ignore file happens to catch them.

**Evidence:** SECRET_NAMES = {".env", ".env.local", ".envrc", "id_rsa", ...}; SECRET_SUFFIXES = (".pem", ".key", ".p12", ".pfx"). `_hard_skip` does `name in SECRET_NAMES ... name.endswith(SECRET_SUFFIXES)` (ignore.py:84-86) — no prefix/glob handling for `.env.*`. Reproduced: a file `repo/.env.production` (`AKIA_PROD_KEY=abc`) passes is_indexable (rel=.env.production, name not in SECRET_NAMES) and is indexed.

**Suggested fix:** Match the `.env` family by prefix (skip any name starting with `.env` except allowlisted examples like `.env.example`/`.env.sample`), and expand SECRET_SUFFIXES (.crt,.cer,.der,.jks,.keystore,.pkcs8,.asc,.ovpn) and SECRET_NAMES (.npmrc,.pgpass,.netrc,.htpasswd,credentials,*.kdbx). Consider a content-based secret heuristic as defense in depth since exact lists will always lag.

### 9. [MEDIUM] index --name on an already-indexed path silently creates a full duplicate index; search then returns every hit twice and there is no command to remove a repo

`src/local_code_indexer/service.py:226` — api-packaging — panel 3/3 upheld

**Claim:** repos has UNIQUE(name) but no uniqueness or lookup on path, and _upsert_repo only upserts by name. Running 'local-code-indexer index <path>' followed by 'index <path> --name other' (the natural way to rename a repo) creates two repo rows for the same directory, each with a complete copy of files/chunks/FTS rows/vectors: DB size doubles and every search returns duplicate results, one per repo name. ### 11. [MEDIUM] sqlite-vec KNN query always fails; vector search silently degrades to full-table JSON scan

`src/local_code_indexer/service.py:532` — correctness — panel 3/3 upheld

**Claim:** The KNN query in _add_vector_candidates can never execute with the project's locked dependencies (sqlite-vec 0.1.9, SQLite 3.50.4): because the vec0 table is joined to chunk_vector_map/chunks/repos, SQLite never passes the LIMIT to vec0's xBestIndex, so every execution raises sqlite3.OperationalError, which is swallowed at line 561. Every vector/hybrid search therefore runs the brute-force fallback that loads and json.loads every chunk's embedding_json and computes cosine in Python. The ANN index is written on every index run but never read.

**Evidence:** Running the exact SQL from _add_vector_candidates against a freshly indexed DB: "KNN join query FAILED: A LIMIT or 'k = ?' constraint is required on vec0 knn queries." The same query with 'AND v.k = 100' instead of LIMIT succeeds ("KNN join with k= OK, rows: 1"). End-to-end confirmation: a repo-filtered vector search returned score 2.1002 = cosine(0.70007) x 3.0, the JSON-fallback scoring formula (similarity*3.0), not the sqlite-vec formula 3.0/(1+distance) which would give 1.69 for that pair — proving the fallback ran even with sqlite_vec loaded.

**Suggested fix:** Replace the LIMIT with an explicit k constraint the planner forwards to vec0: 'WHERE v.embedding MATCH ? AND v.k = ?' (demonstrated working), or run the KNN in a bare subquery over chunk_vectors and join afterward. When doing so, note the repo filter then applies AFTER the top-k selection — over-fetch (k = limit * fan-out) or scope the KNN per repo, otherwise a repo-filtered search can miss matches whose global rank exceeds k. Also log the OperationalError instead of silently swallowing it, so a dead ANN path is visible.

### 12. [MEDIUM] Line-number convention mismatch: chunking/read_file use str.splitlines() while symbol lines count \n — symbols point at the wrong lines

`src/local_code_indexer/chunking.py:177` — correctness — panel 3/3 upheld

**Claim:** chunk_file_text (chunking.py:177) and read_file (service.py:679) compute line numbers via str.splitlines(), which splits on \f, \v, \x85,  ,   in addition to \n. But _regex_symbol_definitions (chunking.py:151) counts only '\n', and tree-sitter rows (_node_start_row) also increment only on newlines. For any file containing a form feed (common page-break convention, e.g. in CPython sources) or   in a JS string, the two conventions diverge: the symbols table line no longer matches read_file/chunk line numbers, search line_range values shift, and the snap-span/symbol-to-chunk mapping in _insert_symbols compares newline-based lines against splitlines-based chunk bounds.

**Evidence:** Indexed pages.py containing 'x = 1\ny = 2\f\nz = 3\ndef target_fn():\n    return 1\n' (5 \n-lines, 6 splitlines-lines). symbols(query='target_fn') returned line 4, but read_file(start_line=4, end_line=4) on the same service returned 'z = 3' — the def is at splitlines-line 5. The tool contradicts itself within one indexed file.

**Suggested fix:** Standardize on physical newline counting: use text.split('\n') instead of str.splitlines() in chunk_file_text and in read_file, matching the tree-sitter and regex conventions (and what editors/agents expect when jumping to a line).

### 14. [MEDIUM] Embedding-dimension change permanently and silently disables sqlite-vec, with no recovery path

### 15. [MEDIUM] Whole-repo write transaction spans per-chunk network calls; concurrent writers fail with 'database is locked'

`src/local_code_indexer/service.py:186` — integrity — panel 3/3 upheld

**Claim:** index_repo holds a single SQLite write transaction (implicit BEGIN at the _upsert_repo insert, commit at line 215) for the entire run, including one Ollama HTTP round-trip per chunk (up to 10s timeout each) — so the write lock can be held for minutes to hours on a large repo. _connect() uses sqlite3.connect's default 5-second busy timeout, so any second writer (a watch on another repo sharing the default DB, or a concurrent `index` command) raises sqlite3.OperationalError: database is locked, which kills that process (and a watch loop, per the missing error handling). WAL keeps MCP readers safe, but connections are also never explicitly closed — `with conn` commits/rolls back without closing, relying on CPython refcount finalization.

**Evidence:** service.py:186 `with self._connect() as conn:` wraps the full file loop with _embed_chunk network calls inside (line 303 via _insert_chunk at line 209); commit only at line 215. service.py:78 `conn = sqlite3.connect(self.db_path)` sets no timeout and no PRAGMA busy_timeout. No conn.close() anywhere; every public method (search, status, list_files, read_file, symbols, index_repo) also calls self.init() first, opening a second never-closed connection per operation.

**Suggested fix:** Compute embeddings outside the transaction (or commit in per-file batches), set a generous busy timeout (sqlite3.connect(..., timeout=30) or PRAGMA busy_timeout=30000), and wrap connections in contextlib.closing so they are deterministically closed. Per-file batch commits also shrink the blast radius of finding 2's rollback.

### 18. [LOW] Empty or trivial query earns every chunk a 4.5 path score — search('') returns arbitrary results with confident scores

`src/local_code_indexer/service.py:600` — correctness — panel 3/3 upheld

**Claim:** _add_path_symbol_scores awards path_score = 4.5 when 'query_lower in path_lower'.

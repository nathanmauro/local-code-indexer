# Post-release delta audit — 2026-06-19

Adversarial review of the code added after the initial release commit `a6bc548`.

**Scope:** only `src/local_code_indexer/service.py`, `src/local_code_indexer/embeddings.py`,
and `src/local_code_indexer/config.py` as shown by `git diff a6bc548..HEAD -- src/`.
The 19 findings from `docs/audit-2026-06-10.md` were treated as already fixed and were
not re-audited.

**Method:** read the June 10 audit for evidence standard, then read `README.md`,
`docs/decisions/0001-embedding-backend-ollama.md`, the three scoped source files,
and the existing service/embedding tests. Baseline before edits was 53 passing tests and
ruff clean. Each confirmed finding below was reproduced with a failing pytest regression
against `.venv/bin/python`; fixes were limited to the scoped source files.

**Result: 4 confirmed, 6 rejected.**

## Confirmed findings

### 1. [HIGH] Backend swaps with the same model name and dimension can silently reuse stale embeddings

`src/local_code_indexer/service.py:411` — data-integrity

**Claim:** `_can_skip_unchanged_file` compared only file hash, stored model name, vector
dimension, and embedding JSON dimension. Switching from one local backend to another
with the same model string and dimension, for example Ollama `nomic-embed-text` to an
OpenAI-compatible localhost server using the same model name, could skip unchanged
files and keep old-backend vectors. ADR 0001 explicitly says vectors from different
backends/quantizations are not comparable.

**Evidence:** Added `tests/test_service.py:380`
(`test_same_model_backend_change_forces_reindex`). The test indexes with a fake
`ollama` backend that stores marker vector `1.0`, deletes `embed_backend` to simulate a
database created before backend identity tracking, then indexes unchanged content with a
fake `openai` backend that would store marker `2.0`. Before the fix:

```text
assert result["indexed_files"] == 1
E       assert 0 == 1
```

The unchanged file was skipped and retained the old marker.

**Fix applied:** Track a stable local embedding backend identity from `api`, `base_url`,
and `model` (`_embedder_backend`, `src/local_code_indexer/service.py:479`) and persist it
only at the successful end of `index_repo` (`service.py:303`). Missing or mismatched
stored backend identity now makes `_can_skip_unchanged_file` return `False`
(`service.py:437`), forcing a safe one-time reindex for legacy databases.

### 2. [HIGH] Interrupted same-dimension model swaps can mark the new model complete before stale files are reindexed

`src/local_code_indexer/service.py:727` — data-integrity

**Claim:** `_ensure_vector_table_for_write` updated the stored `embed_model` during the
first vector write of a model swap. With per-file commits, an exception after the first
file could leave `embed_model = model-b` while later files still contained `model-a`
embedding JSON of the same dimension. The next run saw stored model and current model
as equal, so it skipped stale unchanged files permanently.

**Evidence:** Added `tests/test_service.py:406`
(`test_interrupted_same_dimension_model_change_retries_stale_files`). It indexes two
files with `model-a`, starts a `model-b` reindex, monkeypatches `_upsert_file` to raise
after the first file has committed, then retries with `model-b`. Before the fix:

```text
assert result["indexed_files"] == 2
E       assert 0 == 2
```

Both files were skipped on retry even though one still had the old marker.

**Fix applied:** `_ensure_vector_table_for_write` now handles only dimension schema
changes and no longer writes model identity mid-run (`service.py:727`). `index_repo`
persists `embed_model` and `embed_backend` only after all files and missing-file cleanup
complete (`service.py:303`), so an interrupted run leaves the old identity in settings
and the next run heals every unchanged file.

### 3. [MEDIUM] Incremental unchanged-file skipping is disabled when sqlite-vec is unavailable

`src/local_code_indexer/service.py:411` — correctness

**Claim:** `_can_skip_unchanged_file` required `settings.vector_dim` to be present and
equal to the embedder dimension. When `sqlite-vec` is unavailable, `_upsert_vector`
returns before setting `vector_dim`, even though `embedding_json` is stored. That made
every unchanged file re-embed on every index pass in JSON-fallback mode.

**Evidence:** Added `tests/test_service.py:445`
(`test_unchanged_files_skip_when_sqlite_vec_unavailable`) and monkeypatched
`local_code_indexer.service.sqlite_vec = None`. Before the fix:

```text
assert second["indexed_files"] == 0
E       assert 1 == 0
```

The second index pass reprocessed an unchanged file and called the embedder again.

**Fix applied:** `_can_skip_unchanged_file` now uses the known embedder dimension when
available, falls back to stored `vector_dim` when present, and finally validates the
dimensions already stored in each chunk's `embedding_json` (`service.py:434`). This
preserves safe incremental skips even without sqlite-vec.

### 4. [MEDIUM] OpenAI-compatible batch embeddings ignore response indexes and can attach vectors to the wrong chunks

`src/local_code_indexer/embeddings.py:79` — data-integrity

**Claim:** The OpenAI-compatible `/v1/embeddings` response shape includes per-item
`index` fields. `LocalEmbedder.embed_batch` used the response list order directly, so a
compatible local server that returns data out of order can assign vector B to chunk A and
vector A to chunk B.

**Evidence:** Added `tests/test_embeddings.py:181`
(`test_openai_api_embed_batch_honors_response_indexes`) with a fake localhost response
whose `data` list is reversed but whose `index` fields identify the original inputs.
Before the fix:

```text
assert [[0.3, 0.4], [0.1, 0.2]] == [[0.1, 0.2], [0.3, 0.4]]
```

**Fix applied:** `LocalEmbedder.embed_batch` now sorts OpenAI-compatible response items
by integer `index` when all items provide one, rejects non-contiguous indexes by returning
per-text `None`, and keeps the existing batch-failure behavior (`embeddings.py:81`).

## Rejected findings (reproduced/refuted; not acted on)

- (integrity) The circuit breaker counts breaker-skipped chunks as embedding failures —
  rejected. Existing `tests/test_service.py:491` plus a scripted repro with eight files
  and a failing batch embedder showed `breaker_calls 5`, `breaker_failures 5`,
  `breaker_indexed_chunks 8`, and `breaker_degraded True`; chunks skipped after the
  breaker tripped were not counted as failures.

- (integrity) Per-file commit still holds a SQLite write lock during embedding calls —
  rejected. A scripted repro used an embedder that opened a second SQLite connection and
  wrote to `settings` during `embed()`. The write succeeded (`lock_probe_setting ok`)
  while `index_repo` completed, confirming embedding runs outside an active write
  transaction.

- (correctness) Batch-size chunking can exceed the configured cap — rejected. Existing
  `tests/test_service.py:437` forces a 66-chunk file and confirms all batches are length
  `<= 64` with one exact 64-chunk batch.

- (correctness) Wrong-length batch responses can desynchronize chunks and vectors —
  rejected. Existing `tests/test_embeddings.py:126` and service batching behavior return
  `[None] * len(texts)` on wrong-length responses, and `_embed_chunks_for_run` verifies
  batch length before accepting vectors.

- (security) Env-configured embedding URLs can point at hosted APIs — rejected. Existing
  `tests/test_embeddings.py:140` and `tests/test_embeddings.py:148` verify both Ollama
  and OpenAI-compatible paths reject non-loopback hosts before making an HTTP request.

- (correctness) Disabled embeddings report degraded indexes — rejected. Existing
  `tests/test_service.py:519` verifies `LOCAL_CODE_INDEXER_DISABLE_EMBEDDINGS=1` indexes
  without embeddings and reports `degraded: false`.
